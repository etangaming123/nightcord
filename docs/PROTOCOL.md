# Nightcord Protocol

Version: `0.2`

This document is the single source of truth for the wire format between the
Nightcord client (GitHub Pages, vanilla JS) and a Nightcord server (Python).
Both `client/js/protocol.js` and `server/protocol.py` should be implemented
directly against this spec — if they disagree, this file wins and both get
fixed to match it.

## History

Each protocol version arrived with one commit on `main`, named in the middle column.

| Version | Commit | What it added |
|---|---|---|
| 0.2 | Chat server and web client | Accounts, guilds, text channels and messages over one WebSocket. |

---

## 1. Terminology

- **Server** — a single running `nightcord_server.py` process, reachable at
  an IP/hostname:port. Equivalent to "an instance," not a Discord server.
- **Guild** — a Discord-server-equivalent space living inside a Server. Has
  its own channels, members, and owner. A Server can host many Guilds.
- **Server owner** — one autogenerated account per Server, for server-wide
  config/testing only. Not a normal user account.
- **Guild owner** — the user who created a given Guild; configures that
  Guild's settings.

---

## 2. Transport

- Single persistent WebSocket connection per client, `wss://host:port/ws`.
- All messages, both directions, are UTF-8 JSON text frames.
- Every message is an object with a top-level `type` string and a `payload`
  object. No positional/array-based messages.

```json
{ "type": "message.send", "payload": { "channel_id": "...", "content": "..." } }
```

- A client → server message may include an `id` (string or number, chosen
  by the client). Every direct response to that request echoes the same `id`
  so the client can correlate request/response.
- A request of type `X` is answered with exactly one of:
  - `X.result` — success, payload as documented below, or
  - `X.error` — failure, payload `{ code, message }` (see §9).
  Exception: the auth requests (`auth.register`, `auth.login`,
  `auth.resume`) answer with `auth.ok` / `auth.error`.
- A frame that isn't valid JSON, lacks `type`/`payload`, or names an unknown
  `type` is answered with type `error` (payload `{ code, message }`, code
  `bad_request` or `unknown_type`).
- Server → client messages without an `id` are unsolicited events
  (`message.new`, `presence.update`, `channel.created`, …).
- Maximum frame size is 64 KB.
- Only `server.info` and `auth.*` may be sent before authentication;
  anything else gets `X.error` / `not_authenticated`.

---

## 3. Connection & Auth Flow

1. Client opens the WebSocket to the target Server.
2. Client sends `auth.login` or `auth.register` (or `auth.resume` with a
   stored session token).
3. Server responds `auth.ok` (with session token + basic profile) or
   `auth.error`.
4. Client sends `guild.list` to get the Guilds this account belongs to.
5. When the user opens a specific Guild, client sends `channel.list`,
   `guild.members` and `presence.list` for it.
6. Client sends `channel.join` for the channel currently in view; server
   starts streaming `message.new` events for that channel to this client.

A client is only ever "in" (subscribed to live messages for) the channels
it has explicitly joined — switching channels sends `channel.leave` for the
old one.

### Session resumption
- On successful `auth.login`/`auth.register`, server issues a `session_token`
  (opaque string). Client stores it (localStorage, scoped per saved server).
- On reconnect, client sends `auth.resume` with the stored token instead of
  re-prompting for a password. If the token is invalid/expired, server
  responds `auth.error` with `code: "session_expired"` and client falls
  back to the login screen.
- Sessions expire after 30 days without use (sliding expiry — every
  successful `auth.resume` extends it). `auth.logout` revokes the token.

## 4. Data Models

### User (server-scoped account)
```json
{
  "user_id": "string",
  "username": "string",
  "created_at": "ISO8601",
  "is_server_owner": false
}
```
Password is never sent to the client after registration; server stores only
a bcrypt hash.

### Server config (server-wide, owner-controlled)
```json
{
  "server_name": "string",
  "guild_creation": "off | on",
  "account_creation": "off | request | on",
  "guild_list_visible": true
}
```
`server_name` is read-only over the protocol (set in the server's config
file). Defaults: `guild_creation: "on"`, `account_creation: "on"`,
`guild_list_visible: true`.
`guild_list_visible` gates whether a Server-wide "open guild list" can exist
at all — an individual Guild's own `listed` flag (below) still needs to be
true for it to actually appear.

### Guild
```json
{
  "guild_id": "string",
  "name": "string",
  "owner_user_id": "string",
  "listed": false,
  "created_at": "ISO8601"
}
```

### Channel
```json
{
  "channel_id": "string",
  "guild_id": "string",
  "name": "string",
  "position": 0
}
```

### Message
```json
{
  "message_id": "string",
  "channel_id": "string",
  "author_user_id": "string",
  "author_username": "string",
  "content": "string",
  "sent_at": "ISO8601"
}
```
No `edited_at`/`deleted` fields in v1 — editing/deletion are out of scope.

### Member (as returned by `guild.members`)
```json
{
  "user_id": "string",
  "username": "string",
  "role": "owner | member"
}
```

### IDs
All `*_id` values are snowflake-style integers (`ms_since_epoch << 12 | seq`)
serialized as decimal strings. They sort by creation time, so
`before_message_id` pagination is a plain numeric `<` comparison. Clients
must treat them as opaque strings otherwise.

### Limits
| field | rule |
|---|---|
| username | 3–32 chars, `[A-Za-z0-9_.-]`, unique case-insensitively |
| password | 8–72 bytes UTF-8 (bcrypt limit) |
| message `content` | 1–2000 chars after trimming |
| guild `name` | 1–100 chars |
| channel `name` | 1–32 chars, `[a-z0-9_-]` (client lowercases / replaces spaces with `-`) |
| history `limit` | default 50, max 100 |

### Membership / role (Phase-2-ready stub)
```json
{
  "guild_id": "string",
  "user_id": "string",
  "role": "owner | member",
  "ghost": false
}
```
`role` is intentionally a bare enum for v1 (just `owner`/`member`) so a
richer role system can extend it later without a schema break. `ghost: true`
marks a Server-owner override join (see §7) — clients must exclude any
membership record with `ghost: true` from member-list rendering.

## 5. Message Types

### Auth
| type | direction | payload |
|---|---|---|
| `auth.register` | C→S | `{ username, password }` |
| `auth.login` | C→S | `{ username, password }` |
| `auth.resume` | C→S | `{ session_token }` |
| `auth.request_account` | C→S | `{ username, password, note? }` — used when server's `account_creation` is `request` |
| `auth.request_account.result` | S→C | `{ status: "pending" }` |
| `auth.ok` | S→C | `{ session_token, user }` |
| `auth.error` | S→C | `{ code, message }` |
| `auth.logout` | C→S | `{}` — revokes the current session token |
| `auth.logout.result` | S→C | `{}` |

### Server info / config
| type | direction | payload |
|---|---|---|
| `server.info` | C→S | `{}` — request server config/name/policy, sendable pre-auth |
| `server.info.result` | S→C | `ServerConfig` plus `protocol_version` (e.g. `"0.2"`) |
| `server.config.update` | C→S | partial `ServerConfig` (excluding `server_name`) — **server-owner only** |
| `server.config.update.result` | S→C | `{ config: ServerConfig }` |

### Guilds
| type | direction | payload |
|---|---|---|
| `guild.list` | C→S | `{}` — guilds the authenticated user belongs to |
| `guild.list.result` | S→C | `{ guilds: [Guild] }` |
| `guild.create` | C→S | `{ name }` — rejected with `guild_creation_disabled` if `guild_creation` is off (unless requester `is_server_owner`) |
| `guild.create.result` | S→C | `{ guild: Guild, channels: [Channel] }` — new guild starts with one `general` channel |
| `guild.public_list` | C→S | `{}` — only returns guilds where `listed: true` **and** server's `guild_list_visible: true` |
| `guild.public_list.result` | S→C | `{ guilds: [Guild] }` |
| `guild.join_by_code` | C→S | `{ invite_code }` |
| `guild.join_by_code.result` | S→C | `{ guild: Guild }` |
| `guild.join_by_id` | C→S | `{ guild_id }` — only valid from the public list or server-owner override |
| `guild.join_by_id.result` | S→C | `{ guild: Guild }` |
| `guild.owner_override_join` | C→S | `{ guild_id }` — **server-owner only**; joins silently, sets `ghost: true` |
| `guild.owner_override_join.result` | S→C | `{ guild: Guild }` |
| `guild.leave` | C→S | `{ guild_id }` — not allowed for the guild owner |
| `guild.leave.result` | S→C | `{}` |
| `guild.members` | C→S | `{ guild_id }` |
| `guild.members.result` | S→C | `{ members: [Member] }` — **excludes** `ghost: true` memberships |
| `guild.config.update` | C→S | `{ guild_id, name?, listed? }` — **guild-owner only** |
| `guild.config.update.result` | S→C | `{ guild: Guild }` |
| `guild.invite.create` | C→S | `{ guild_id }` — **guild-owner only** for v1 |
| `guild.invite.create.result` | S→C | `{ invite_code }` |
| `guild.updated` | S→C | `Guild` — event to online members after `guild.config.update` |
| `guild.member_joined` | S→C | `{ guild_id, member: Member }` — event; never sent for ghost joins |
| `guild.member_left` | S→C | `{ guild_id, user_id }` — event; never sent for ghost memberships |

`guild.list.result` includes guilds where the user holds a ghost membership.
The Guild objects in `guild.list.result`, `guild.create.result` and the
three `guild.join_*` / `guild.owner_override_join` results additionally
carry `ghost: true|false` for the requesting user. Joining normally (invite
or public list) while holding a ghost membership upgrades it to a regular,
visible membership.

### Channels
| type | direction | payload |
|---|---|---|
| `channel.list` | C→S | `{ guild_id }` |
| `channel.list.result` | S→C | `{ channels: [Channel] }` |
| `channel.join` | C→S | `{ channel_id }` — subscribe to live messages |
| `channel.join.result` | S→C | `{}` |
| `channel.leave` | C→S | `{ channel_id }` |
| `channel.leave.result` | S→C | `{}` |
| `channel.history` | C→S | `{ channel_id, before_message_id?, limit? }` — scroll-back |
| `channel.history.result` | S→C | `{ messages: [Message], has_more }` — messages oldest-first |
| `channel.create` | C→S | `{ guild_id, name }` — **guild-owner only** |
| `channel.create.result` | S→C | `{ channel: Channel }` |
| `channel.update` | C→S | `{ channel_id, name?, position? }` — **guild-owner only** |
| `channel.update.result` | S→C | `{ channel: Channel }` |
| `channel.delete` | C→S | `{ channel_id }` — **guild-owner only**; deletes its messages too |
| `channel.delete.result` | S→C | `{}` |
| `channel.created` | S→C | `Channel` — event to online members of the guild |
| `channel.updated` | S→C | `Channel` — event to online members of the guild |
| `channel.deleted` | S→C | `{ guild_id, channel_id }` — event; subscribers are unsubscribed |

A client may be joined to at most one channel at a time per connection;
`channel.join` implicitly leaves any previously joined channel.

### Messaging
| type | direction | payload |
|---|---|---|
| `message.send` | C→S | `{ channel_id, content }` — rate-limited to 5 per 5 s per connection |
| `message.send.result` | S→C | `{ message_id }` |
| `message.new` | S→C | `Message` — pushed to every client currently joined to that channel (including the sender) |

### Presence
| type | direction | payload |
|---|---|---|
| `presence.list` | C→S | `{ guild_id }` |
| `presence.list.result` | S→C | `{ online_user_ids: [string] }` — **excludes** any `ghost: true` presence |
| `presence.update` | S→C | `{ guild_id, user_id, status: "online" \| "offline" }` — broadcast on join/leave; suppressed entirely for ghost sessions |

A user is online in a guild while they have at least one authenticated
connection and a non-ghost membership in it. `presence.update` is sent to
the other online members of each such guild when the user's first
connection authenticates (`online`) and when their last one closes
(`offline`).

### Moderation (stubbed, not implemented in v1)
Reserved type prefix `moderation.*` (e.g. `moderation.kick`, `moderation.ban`)
— not defined yet, left as a placeholder namespace so Phase 2 doesn't
collide with anything above.

## 6. Guild Discovery & Joining — decision table

| Path | Requirement |
|---|---|
| Invite code | Always available regardless of any listing settings |
| Open list | Requires **both** `server.guild_list_visible: true` **and** the specific guild's `listed: true` |
| Server-owner override | Always available to the server-owner account only, via `guild.owner_override_join`; results in a `ghost` membership |

---

## 7. Server-owner override behavior

- Server owner may call `guild.owner_override_join` for **any** guild on the
  Server at any time, bypassing invite codes and `listed` status.
- The resulting membership row has `ghost: true`.
- Server must exclude `ghost: true` rows from:
  - `presence.list.result`
  - any `presence.update` broadcasts
  - member-list-adjacent data in general
- The server owner still receives `message.new` for channels they've
  ghost-joined, and may read history, but a ghost membership is
  **read-only**: `message.send`, `channel.create/update/delete`,
  `guild.config.update` and `guild.invite.create` are rejected with
  `forbidden`. (Resolved in v0.2.)
- A ghost membership may be dropped with `guild.leave`; no event is sent.

---

## 8. Account creation policy

Server-wide, owner-toggled via `server.config.update`:

- **off** — `auth.register` always rejected with `auth.error` /
  `code: "registration_closed"`.
- **request** — `auth.register` rejected; client should instead use
  `auth.request_account`, which creates a `pending` row. Server owner
  reviews via a separate (currently console-based, v1) approval flow, not
  yet given its own protocol messages here — to be added when the
  server-owner console tooling is designed. Until approved, `auth.login`
  for that username fails with `registration_pending_approval`; a rejected
  request fails with `invalid_credentials`.
- **on** — `auth.register` works normally.

In `request` mode, `auth.register` fails with `registration_closed`
(clients read `account_creation` from `server.info` to pick the right
form). `auth.request_account` is only accepted in `request` mode; in `off`
mode it fails with `registration_closed`, in `on` mode with `bad_request`.
The username `owner` is reserved for the server-owner account.

## 9. Errors

Any `*.error` response uses:
```json
{ "code": "snake_case_machine_code", "message": "human-readable string" }
```
Known codes: `invalid_credentials`, `session_expired`,
`registration_closed`, `registration_pending_approval`, `invite_invalid`,
`not_found`, `forbidden` (e.g. non-owner calling an owner-only action),
`bad_request` (malformed frame or payload), `unknown_type`,
`not_authenticated`, `username_taken`, `invalid_username`,
`invalid_password`, `content_too_long`, `rate_limited`,
`guild_creation_disabled`, `already_member`, `internal_error` (unexpected
server-side failure; safe to retry).
This list will grow during implementation — append here rather than
inventing undocumented codes.

## 10. Explicitly deferred (Phase 2 / later)

Documented here so the schema above leaves room, without being built yet:

- Granular roles/permissions beyond `owner`/`member`
- Additional moderation actions (`moderation.*` namespace reserved)
- Message editing/deletion
- File/image attachments
- Direct messages (user-to-user, outside any guild)
- Voice/video
- Read receipts — **permanently out of scope**, not just deferred
- Choice of TLS strategy (self-signed vs. Cloudflare Tunnel) at server
  setup time — v1 ships self-signed only; the choice mechanism is future
  work
